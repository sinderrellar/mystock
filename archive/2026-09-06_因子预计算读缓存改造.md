# 因子计算「预计算+读缓存」改造 —— 消除 review 路径的重复重算

## 背景 / 需求（老板 2026-09-06）

老板反馈「数据源这里，因子每次都要重新算，而且计算量很大」，问业界做法。排查后结论：项目已有 `precompute_history.py` 每天把因子落库到 `stock_factors`，但 `review()` 的观察池路径**现场重算**没读缓存。老板拍板：①改 review 因子路径读缓存；②加行业横截面统计预计算。数据源选「商业组因子」（与下游 alpha_context/entry_engine 一致）。

## 改了什么

### Item 1：review 观察池因子读 `stock_factors` 商业组（`scripts/portfolio_strategy.py`）

- 新增 `_latest_factor_trade_date()`：取 `stock_factors` 集合最新 `trade_date`（本次 review 内缓存一次）。用「集合最新日期」做新鲜判据而非「距今天数」——长假期间 precompute 停在节前最后交易日，那是可用最新数据，不该误判过期。
- 新增 `_factor_from_cache(code)`：读该股**所属商业组**的 `{composite_score, factor_scores}`；未命中或非最新返回 `None`，触发现场 `calculate_composite_score` 兜底。
- `review()` 观察池循环的多因子块改为「先读缓存，miss 才兜底重算」。

### Item 2：行业横截面统计预计算（`scripts/precompute_history.py` + `scripts/pyramid_multifactor_strategy.py`）

- precompute 因子步骤末尾新增第 7 步：`pyramid._build_industry_stats()` 结果写入新集合 `stock_industry_stats`（键 `trade_date`，字段 `stats`）。
- `PyramidMultifactorStrategy._get_industry_stats()` 优先读 `stock_industry_stats`（新增 `_load_industry_stats_cache()`），miss 才现场全表扫描 `basic_info`。

## 为什么这样改

- 研究过程/因子这类「重、且一天只变一次」的数据，业界标准做法就是**离线物化 + 请求路径只读**（因子库范式），这正是 precompute 已经在做、但 review 读路径漏接的部分。
- 商业组因子是该股所处行业/风格对应的权重+评分，比现场硬编码 default 权重更贴合，且与 `alpha_context`（`portfolio_strategy.py` 早已读 `stock_factors.factors[group]`）一致，消除「卡片显示 default 因子、下游用组因子」的现有不一致。

## 怎么验证

1. `py_compile` 三个改动文件通过。
2. `_factor_from_cache('600941')` 命中返回 `{composite_score:0.422, factor_scores:{value:0,growth:0.0,quality:0.0,momentum:0.703}}`；`_factor_from_cache('999999')` 返回 `None`（走兜底）；`_latest_factor_trade_date()` = `2026-09-04`。
3. `_build_industry_stats()` 产出 97 个行业（耗时 0.04s），写入 `stock_industry_stats` 后新实例 `_get_industry_stats()` 读缓存命中、结果一致（0.002s）。
4. 全量 `review()` 跑通（28.6s，无异常，返回结构完整）。
5. `review()` 内 `PortfolioStrategy` 每次新建，`_latest_factor_td` 只缓存本次 review 内，无跨请求陈旧问题。

## 重要发现（如实上报，未做静默降级）

**因子本身不是「计算量很大」的元凶。** 实测 `review()` 单只持仓各信号耗时：

| 信号 | 耗时 |
|------|------|
| `_factor_signal`（四因子） | 0.19s |
| `_trend_signal`（趋势） | 0.93s |
| `_event_signal`（新闻事件，LLM 情绪） | **9.71s** |
| `sector_heatmap` | 4.7s |
| `get_market_sentiment` | 3.5s |

- 四因子单次 `calculate_composite_score`（行业统计已缓存）仅 **0.001s**；真正拖慢 review 的是 **`_event_signal` 每次对每只持仓拉 10 条新闻并跑 LLM 情绪（9.7s/只）**，加上 sector_heatmap 与 market_sentiment。
- Item 1 当前观察池为 0 只，收益主要体现在「以后有观察池时」+ 一致性修正；Item 2 每次省约 0.04s 全表扫描。两者是正确的架构收敛，但**不是本次性能瓶颈**。

**下一步建议**（若要真正降 review 耗时）：把 `_event_signal` 的新闻 LLM 情绪也做成「日级预计算 + 读缓存」（新闻情绪一天不会变），复用与 Item 1/2 相同的物化范式；sector_heatmap 与 market_sentiment 同样可日级缓存。待老板确认后另排。

## 局限

- `_factor_signal`（持仓决策卡的富因子，含 factor_details/llm_context/interpretation）仍在每次 review 现场重算——`stock_factors` 只存 composite_score + factor_scores，无法重建这些富字段，且实测仅 0.19s，暂不改。
- `stock_industry_stats` 只在 `run_factors` 分支写入（与因子同批 daily）；历史批量回填会把当前 basic_info 的横截面统计盖到历史 trade_date，但 review 只读最新 trade_date，无影响。
