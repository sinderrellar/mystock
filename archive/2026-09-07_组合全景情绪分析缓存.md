# 组合全景情绪分析缓存

日期：2026-09-07

## 为什么改

老板反馈「刷新组合全景」响应时间偏长。cProfile 定位根因：

- `review()` 全程约 48s，其中**情绪分析是绝对瓶颈**：`_event_signal` → `analyze_sentiment_batch` → `_call_llm`（deepseek）约 9s/次，5 只持仓串行约 27s。
- 市场行情数据拉取仅约 0.9s，不是慢点。
- 既有情绪缓存 key 是 `_text_hash(新闻文本)`（`event_driven_strategy.py`），而每次 `get_news` 拉到的新闻都在变，hash 永远 miss，等于没缓存。

老板拍板：**采用缓存方式**。情绪分析只针对持仓（组合全景 `review()` 的 `collect_for_position` 只在 `position_rows` 上跑，观察池不跑情绪）。

## 改了什么

`scripts/strategy_signals.py` 的 `_event_signal`（情绪信号入口）：

1. **新增双层缓存**：按「标的代码 + 市场 + 当日日期」做 key（`300750:A股:2026-09-07`）。
   - **内存缓存** `self._event_cache`：同进程内（`PortfolioStrategy.signal_collector` 单例）跨持仓、跨 review 复用。
   - **MongoDB 缓存** `event_signal_cache` 集合（7 天 TTL，`_id = key`）：跨进程、跨 api_server 重启复用。
2. **只缓存 `available=True` 的结果**：`unavailable`（新闻源暂时失败、未获取到新闻等）多为暂时性失败，缓存会把错误固化一整天，故不缓存、每次重算。
3. 命中缓存时返回副本并加 `cached=True` 标记，供下游/前端识别「当日缓存值」。
4. 新增 4 个私有方法：`_get_event_cache_col`（懒加载集合）、`_event_cache_key`、`_lookup_event_cache`、`_save_event_cache`。

缓存位置选在 `_event_signal`（而非更下层的 `analyze_sentiment_batch`），因为：它同时覆盖「组合全景 review 的持仓」和「`analyze_stock` 单只标的（投资助手/智辩取数底座）」两个场景，收益最广、改动最小。

## 怎么验证

1. `python3 -m py_compile scripts/strategy_signals.py` 通过。
2. **内存缓存单测**（`/usr/bin/python3`，无 pymongo 环境）：同一 collector 实例连续两次 `_event_signal`，第二次命中缓存、`get_news` 只调 1 次，`cached=True`。
3. **MongoDB 持久化单测**（venv python）：实例 A 写入 `999999:TEST:2026-09-07`（测试 code，不污染真实标的），新实例 B（模拟重启）命中、`get_news` 0 次。

## 局限 / 待办

- **首次仍慢**：缓存是「当天首次算一次、之后复用」。每日第一次 review 仍会全量调 LLM（约 30s），当天后续刷新命中缓存（秒回）。跨天（次日）key 变化，自动重新全量算——这是合理的，情绪本应按日更新。
- **`latest_titles` 为当日快照**：命中缓存时，返回的「最新新闻标题」是当天首次算时的快照，非实时。情绪分数/主题/关键词稳定不受影响；前端如需可借 `cached=True` 标注「情绪为当日缓存」。
- 测试写入了一个 `999999:TEST:2026-09-07` 缓存 key（fake 数据），7 天 TTL 自动清理，不影响真实标的；如需立即清理需老板手动 mongo shell 执行（遵守禁删约束）。
- 未在真实 `review()` 上做端到端计时（会真实调 LLM 并写真实缓存）；建议下次连续刷新两次组合全景对比耗时验证。
