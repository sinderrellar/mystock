# 投资助手数据底座补全：持仓上下文 + 资金面/新闻/行业周期透传 + 数据自检层

日期：2026-09-07

## 为什么改

诊断「投资助手」（多轮对话，normal/deep 两档）发现一个反直觉结论：**不是数据不够，是 analyze_stock 已经算好的字段没透传给 LLM**。对照「兆易创新快速体检」（evidence 为空时 LLM 自取数据）逐字段比对，底座缺 4 类数据，导致深度分析要么白联网补、要么丢了用户最关心的持仓信息。

老板拍板 6 项，本归档覆盖其中 5 项实现 + 1 项查证：

1. **持仓上下文**（第 1 项）：查的股票恰好是持仓时，注入数量/成本/止损/止盈/浮盈亏。
2. **moneyflow 主力资金**（第 2 项）：透传。
3. **news + tushare_signals**（第 3 项）：透传。
4. **行业 cycle_score/趋势/宽度/资金流**（第 4 项）：透传。
5. **两套因子算法差别**（第 5 项）：只查证不改，结论见下。
6. **数据自检层**（第 6 项）：主动标注口径矛盾/脏数据。

## 改了什么

### 1. `scripts/debate_engine.py`（核心透传 + 自检）

`get_data_base` 从只抽 4 字段，扩展为抽全 analyze_stock 已算字段：

- **moneyflow**：主力/大单/超大单资金流（tushare，available:true）。
- **news**：新闻原文，最多 5 条、正文压到 160 字（防底座膨胀）。
- **tushare_signals**：回购/股东户数/两融/业绩预告/财务（港股含南向）。
- **pe_percentile_self**：自身历史 PE 分位（stock_signals.pe_percentile，当前为 null 属数据层待补）。
- **cycle**：新增 `_load_cycle_context`，从 `stock_factors` 预计算表取 `group/cycle_score/turnaround_score/industry_trend/industry_breadth/industry_flow/group_composite_score/group_factor_scores`（与 review() 的 alpha_context 同源）。
- **data_quality**：新增 `_data_self_check`，主动标注 6 类异常——52周高 vs 120日高交叉、MACD 全 0、业绩预告越界（如 forecast=1099% 脏数据）、换手率缺失、实时 vs 预计算因子口径差异显著（≥0.15）、预计算因子财务缺失（value/growth/quality 全 0）。

`typing` 导入补 `List`。

### 2. `scripts/debate_session.py`（持仓上下文 + 文本呈现）

- `_build_evidence(code, market, user_id="")`：新增 `user_id` 参数，evidence 结构加 `position` 字段。若该标的恰为用户持仓，注入持仓上下文。
- 新增 `_current_price_from_data`：从底座 quote_snapshot.metrics.regular_market_price / trend_signal.latest_close 提现价。
- 新增 `_position_context(user_id, code, data)`：查 `sim_positions`（`closed != True`），返回数量/可用/成本/币种/止损/止盈/买入逻辑/行业 + 现价/市值/浮盈亏/浮盈亏%/距止损%。查询失败返回 None 不阻断。
- `_evidence_text`：① 数据自检置顶（⚠️ 列出）；② 持仓上下文单独成段；③ 定量底座截断从 5000 提到 12000（配合新字段）。
- `create_session` / `run_debate_turn`（normal 换标识别）传 `user_id`；空 evidence 默认补 `position: None`。

### 3. `scripts/assistant_evidence.py`（deep 模式取数 helper）

带 `--session` 时先读 session 的 `user_id`，再传给 `_build_evidence`，使 deep 模式（LLM 调 helper 取数）同样注入持仓上下文。

## 第 5 项查证：两套因子算法差别

**同一算法，不同参数。** 两套都调 `pyramid_multifactor_strategy.calculate_composite_score`：

| | 实时（llm_context，底座里） | 预计算（stock_factors，快速体检自取） |
|---|---|---|
| 权重 | default {value 0.05, growth 0.3, quality 0.15, momentum 0.5} | 业务组 override_weights（轻资产成长 {0.10/0.45/0.25/0.20}） |
| 评分阶梯 | default（config_complete.yaml） | 业务组 override_scoring（config/轻资产成长.yaml 等） |
| 兆易创新结果 | 综合 0.521，质量 0.2，价值 0.2 | 综合 0.84，质量 0.887，价值 0.6 |

**根因**：`analyze_stock`（portfolio_strategy.py:771）在 `collect_for_position` 时 `fake_position` 的 industry/style 还是空（:775 才补），且 `_factor_signal`（strategy_signals.py:112）没传 `override_weights/override_scoring` → 实时路径永远走 default 权重+default 阶梯，丢掉了业务组校准。`get_factor_weights` 里的 style_weights 匹配实际是死代码（config 无 style_weights 节）。

**结论**：实时因子分（0.521）系统性低于业务组校准分（0.84），质量/价值因子被 default 阶梯压扁。要不要把业务组 override 接进实时路径，由老板定夺（未改）。
