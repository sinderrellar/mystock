# 成交额每日刷新 + 港股 latest_amount 单位修复

日期：2026-09-10

## 背景

体检 9/9 行情时发现可投池缩水（3147 只 vs 正常 5764），一路追查到根因：
`latest_amount`（成交额，万元）唯一的日常更新源是周日 20:00 的 `import-universe-light`，
而它因历史 crontab 用了相对路径 `venv/bin/python`（log 里 47 个 `No such file or directory`）
自初始化后就没再成功跑过，导致成交额停在 9/4 快照。`import-universe-quotes`（工作日 19:00）
用这个陈旧成交额选可投池，越选越偏。

顺带发现港股 2 条（腾讯/小米）的 `latest_amount` 是元单位误存（漏了 /1e4 转换），
显示成 45 万亿。

## 改了什么

### 1. 新增 `import_latest_amount`（data_import_pipeline.py）
- 每天盘后用 Sina 全市场 spot（`ak.stock_zh_a_spot`，一次调用拿全市场）刷新成交额
- 只 `$set` `latest_amount` + `updated_at`，不碰 name/industry/close 等字段（避免副作用）
- 单位：Sina「成交额」是元 → `/1e4` 转万元
- 只更新已有股票，不新增（新增是 import-universe-light 的职责）；幂等可重跑

### 2. `import_universe_quotes` 开头调用（兜底）
- 选可投池前先刷成交额，失败降级沿用旧值、不阻塞日线导入

### 3. crontab 挂载
```
55 18 * * 1-5 cd .../scripts && .../venv/bin/python data_import_pipeline.py import-latest-amount >> ../logs/import.log 2>&1
```
18:55 盘后先刷成交额，19:00 `import-universe-quotes` 用当天收盘成交额选可投池。

### 4. 港股 latest_amount 元→万元（factor_data_import_service.py，3 处代码 + 2 条存量）
| 路径 | 位置 | 修复 |
|------|------|------|
| `_fetch_basic_via_tencent_hk` | fields[37]（成交额·元）| 加 `/1e4` |
| `_fetch_basic_via_eastmoney_hk` | f6（成交额·元）| 加 `/1e4` |
| `_sync_hk_universe_basic` | 成交额（元）| 加 `/1e4` |
| 存量 | 港股 2 条 latest_amount | `$mul 1/1e4` |

## 为什么改

- 成交额是 `import-universe-quotes` 选可投池的唯一排序依据，必须每个交易日刷新，
  不能等周日（且周日 cron 还断过）
- A 股路径都做了 `/1e4`（东财 spot、import_universe_light 都有注释），唯独港股三条路径漏了，
  同源 bug，元单位直接写入导致成交额虚高 1 万倍

## 怎么验证

1. `import-latest-amount` 单跑：成交额刷新 5560 只、跳过 0 只，exit 0
2. `updated_at` 从 9/4 陈旧 → 9/10（5555 只）
3. 港股修复后：腾讯 454650 万元（45.47 亿）、小米 456611 万元（45.66 亿），单位正确
4. 全库 `latest_amount > 200 亿` 残留 = 0
5. `py_compile` 两个脚本均通过

## 局限 / 遗留

- 本次手动跑 `import-latest-amount` 是盘中（10:30）实时值，可投池 2848 只偏低（半天成交额），
  18:55 crontab 会用收盘值恢复到 ~3179 只
- `import-universe-light`（周日）还负责行业编码/名称，体检发现这些**不 stale**（5555/5557 覆盖、
  名称 0 缺失），无需额外修；其 crontab 已是绝对路径，9/14 周日自动恢复运行
- 港股 2 条是 liuyu20 持仓决定的（腾讯+小米），系统只导持仓港股、不做全市场港股，属正常
