# 组合全景提速：修复 sector_radar 热循环重复读盘 config 的 bug

## 背景 / 需求（老板 2026-09-07）

老板反馈「全景组合看起来比以前更慢」。实测 review() 后定位：**不是因子/实时计算慢，而是一个 config 重复读盘的 bug + 几个外部网络请求**。

## 根因（cProfile 坐实）

空仓（0 持仓）下 `review()` 实测 13.8s，cProfile 显示榜首：

```
sector_radar.py:33(_get_radar_config)   被调用 420 次   cumtime 14.1s
yaml/__init__.py:117(safe_load)         428 次           cumtime 14.3s
```

`_get_radar_config()` 在 `compute_heatmap()` 的行业循环里被调用（每行业 ×2：`hot_pct`/`warm_pct` 各调一次），而它每次 `open()` + `yaml.safe_load()` 整个 `config/config_complete.yaml`。约 210 个行业 → 420 次整文件 YAML 解析 ≈ 浪费 7~8s。config 一天都不会变，纯属热循环里重复读盘。

## 改了什么（`scripts/sector_radar.py`）

`_get_radar_config()` 加模块级进程内缓存（`_RADAR_CONFIG_CACHE`），首次读盘后复用：

```python
_RADAR_CONFIG_CACHE: Optional[Dict[str, Any]] = None

def _get_radar_config() -> Dict[str, Any]:
    global _RADAR_CONFIG_CACHE
    if _RADAR_CONFIG_CACHE is not None:
        return _RADAR_CONFIG_CACHE
    ...
    _RADAR_CONFIG_CACHE = cfg.get("pyramid_middle_layer", {}).get("sector_radar", {})
    return _RADAR_CONFIG_CACHE
```

## 怎么验证

1. `py_compile` 通过。
2. 空仓 `review()` 实测：**13.8s → 6.2s**（-55%）。
3. 修复后 cProfile：`_get_radar_config` 不再上榜，榜首变成网络请求（见下）。
4. 后端重启（PID 23118 → 26643），`/api/health` 200。

## 剩余耗时（已定位，未在本改动处理）

修复后空仓 review() 剩 ~6s，全是**外部网络请求**（不是「计算」）：

| 项 | 耗时 | 说明 |
|----|------|------|
| `get_market_sentiment` | ~3.3s | 拉上证/创业板/沪深300 三指数 30 日 K 线 + 北向/融资融券/主力/行业资金流 |
| `get_bars`→`_get_yahoo_bars` | ~2.3s | 3 次 Yahoo 指数 K 线（含 SSL 握手 ~1.1s）；**因 Mongo 日线缓存 3 天未更新（最新 09-04）触发 Yahoo 兜底** |

- 指数 K 线的 Yahoo 兜底是因为 **`precompute_history` 已 3 天没跑**导致 Mongo 日线过期（日志有告警「趋势缓存 3 天未更新」）。每天跑 precompute 后 `get_bars` 直接命中 Mongo，即可省掉这 2.3s。
- 资金流接口是东方财富「准实时」（盘中会变），但组合全景不需要秒级，可日级缓存。

## 结论（回老板「有需要实时计算的数据吗」）

真正需要实时的只有**现价**（且拉取很快）。因子/趋势/新闻情绪/行业动量/市场情绪/指数K线全是**日级数据**，本不该每次 review 现场算/现场拉。慢的三层：① config 循环读盘 bug（本次已修）；② 日线缓存过期→Yahoo 兜底（跑 precompute 即可）；③ 资金流准实时接口（可日级缓存）。
